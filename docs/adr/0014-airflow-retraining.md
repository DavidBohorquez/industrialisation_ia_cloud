# ADR-0014: Orchestrate retraining with Airflow

- **Status:** Accepted
- **Date:** 2026-11-20

## Context

The course asks for an orchestrator that retrains the model. Training is an execution process, not a build step (slide 23): a new model is worth training when enough new data has arrived, which has nothing to do with a code change, so it does not belong in the CI/CD pipeline. The orchestrator sits above training (slide 24), and orchestrating the data flow is one of the practices to follow (slide 17).

The training data now comes from the ERP's PostgreSQL database (ADR-0009), read through the read-only role `ml_reader` on a read replica. The outcome `express_eligible` is written by the ERP some time after the order (ADR-0010): it stays `NULL` until known, and training reads labelled orders only. The ERP simulator writes about one order per second (5 orders every 5 seconds), each batch being one *simulated* day. The training job already exists as an image (`livraison-express-train`, ADR-0008): `python -m livraison_express train` trains `MODEL_VERSION` into the models volume, reads its orders from the source chosen by `ORDER_SOURCE` and `POSTGRES_DSN` (ADR-0013), and refuses a version that already exists.

## Decisions

1. **Apache Airflow 3.4.0, with the official Docker Compose file (CeleryExecutor).** `orchestration/airflow/docker-compose.yaml` is the file published with Airflow 3.4.0: scheduler, dag-processor, api-server (UI and REST API), triggerer, a Celery worker, Redis as the broker and PostgreSQL as Airflow's own metadata database. It is the multi-container architecture of a production Airflow, at the scale of one machine: the scheduler only decides what runs, workers run the tasks. The few changes made to the file are listed in its header and marked where they are, so an upgrade is a diff against the new upstream file.
   Rejected:
   - cron on a machine: runs a command at fixed times, but keeps no history of runs, shows no task states, and the threshold logic and its state would be home-made.
   - a scheduled GitHub Actions workflow: training is execution, not build (slide 23), and CI runners must never reach production data (the ERP replica and its credentials would have to be reachable from GitHub). A new model does not need a code change either (ADR-0006, decision 4).
   - Airflow with the LocalExecutor (`airflow standalone`, or a compose file without Redis and worker): fewer containers and enough for one DAG, but tasks then run inside the scheduler's container, and the file would no longer be the official one.
2. **Airflow orchestrates, our image computes.** The DAG `retrain_express_model` never imports `livraison_express`. The training runs in the training image, started by the `DockerOperator` on the host's Docker engine, exactly like `docker compose run --rm train`. Airflow's Python environment (hundreds of pinned packages) and the application's (ADR-0007) never mix, and the image Airflow runs is the one CI built and tested. The official Airflow image already ships the `docker` and `postgres` providers, so it is used as is, without a custom image.
3. **Trigger: the number of new labelled orders, checked every 10 minutes.** The DAG runs on a schedule (`RETRAIN_SCHEDULE`, default `*/10 * * * *`, `catchup=False`, `max_active_runs=1`), counts the labelled orders, and trains only if the count grew by at least `min_new_labelled_orders` (default 1000, about 17 minutes of simulated orders) since the last successful training. The last count is an Airflow Variable written only after a successful training: a failed training leaves it unchanged, so the next run trains again. A count that goes down (database reset) restarts from 0. The trigger uses neither Airflow's data interval nor the order dates, which are simulated (one day every few seconds): only the data itself says how much is new.
4. **A run has four tasks.**
   1. `count_labelled_orders`: `SELECT count(*) FROM orders WHERE express_eligible IS NOT NULL` through the connection `erp_postgres` (postgres provider hook).
   2. `enough_new_labels`: short-circuit. Below the threshold, the next two tasks are skipped and the run still succeeds.
   3. `train_model`: `DockerOperator` running `TRAIN_IMAGE` with `ORDER_SOURCE=postgres`, `POSTGRES_DSN`, `MODEL_VERSION` and `LOG_LEVEL`, on the network `livraison-net` (to reach host `erp-postgres`), with the volume `MODELS_VOLUME` at `/app/artifacts` and `MLRUNS_VOLUME` at `/app/mlruns` (defaults: `livraison-express-test_models` and `livraison-express-test_mlruns`, the volumes of `docker-compose.test.yml`, so the test API reads what this DAG writes). The training logs are copied into the task log and the container is removed at the end.
   4. `record_labelled_count`: stores the count in the Variable.

   Each training gets a new version `<model_version_prefix>+<UTC date and time of the run>`, e.g. `2.0.0+20261120T173017` (default prefix `2.0.0`, the model version of the canonical vocabulary): SemVer build metadata (same model recipe, newer data), unique per run, and a valid folder name for the model repository. It is built from `run_after`, which every Airflow 3 run has (a manual run may have no logical date, hence no `ts_nodash`). The training task has no retries: a retry would reuse the version, which already exists if the first attempt saved the model.
5. **One read-only connection to the ERP database.** `AIRFLOW_CONN_ERP_POSTGRES` (an environment variable built from `ML_READER_PASSWORD`) defines the connection `erp_postgres` for the role `ml_reader`. It serves the SQL check and gives the training container its `POSTGRES_DSN`, built by a template macro when the task starts: the password is never in the DAG file, in XCom or in the serialized DAG, and the DSN is masked (`***`) in the logs and in the UI's rendered template. Only the Celery worker joins `livraison-net`; Airflow's metadata database stays on Airflow's own network, where its service name `postgres` cannot clash with the ERP's.
6. **Security: the Docker socket.** The worker mounts `/var/run/docker.sock` to start the training container. Access to that socket is root-equivalent on the host: whoever can change a DAG or run a task can start any container, privileged ones included. Accepted on a developer machine, where the DAG files come from the repository and the UI is bound to `127.0.0.1`. In the cloud, the same DAG would use the `KubernetesPodOperator` (one pod per training, no socket, permissions given by the cluster) or a managed training job. The training container keeps the image's non-root user; the `DockerOperator` cannot drop Linux capabilities as the root `docker-compose.yml` does.
7. **Promotion stays manual.** The DAG writes a candidate version; the API keeps serving the `MODEL_VERSION` of its own configuration. Promoting means reading the candidate's model card (`metadata.json`, MLflow run), then changing the API's `MODEL_VERSION` and restarting it. Automatic promotion would need an evaluation gate (compare the candidate with the served model on the same recent data) and a model registry: a later step.

## Consequences

- The stack is 7 long-running containers, plus the training container while it runs. Airflow asks for at least 4 GB of memory for Docker, 2 CPUs and 10 GB of disk; the `apache/airflow:3.4.0` image is about 3.2 GB unpacked. Measured on a developer machine: healthy about one minute after `airflow-init`, and a training run (container start, training, MLflow) takes about 30 seconds.
- The official file requires a `.env` (copied from `.env.example`). Prerequisites: the training image, the network `livraison-net` and the ERP database. Without the database, `count_labelled_orders` fails (`failed to resolve host 'erp-postgres'`) and nothing else runs.
- New DAGs start paused (`DAGS_ARE_PAUSED_AT_CREATION` in the official file): `retrain_express_model` has to be unpaused once.
- Candidate models accumulate in the volume, one folder per training (a few kB each today); removing old ones is manual.
- The recorded count is measured before the training, which may read a few more labels: the next training can come slightly early, never late.
- `docker compose down -v` deletes Airflow's database, the Variable included: the next run counts every labelled order as new and trains.
- A scoring DAG (out of scope) could not select its orders with Airflow's `data_interval` either, since order dates are simulated: it would keep a watermark, the last processed order sequence (`ERP-%08d`), stored the same way as the label count.
- On Linux, the worker needs the socket's group (`DOCKER_GID` in `.env`); Docker Desktop needs nothing.
- Upgrading Airflow: download the new official file and re-apply the changes listed in its header.
